GUÍA · OAUTH 2.0 · FLASK

Login con Google,
de cero a sesión activa.

Siete fases para añadir autenticación con Google a una app Flask: credenciales en Google Cloud, callback, intercambio de código por token y usuario persistido en SQLite. Basada en una implementación que funciona — cada fase enlaza su archivo real.

Las tres llamadas del intercambio: código → token → perfil.

EL PROTOCOLO EN CUATRO SALTOS

  1. 1Tu appredirige al navegador hacia Google con tu client_id y la lista de scopes.
  2. 2Googleautentica a la persona, pide consentimiento y devuelve un code a tu callback.
  3. 3Tu servidorcanjea el código por un access_token — con tu client_secret, sin exponerlo nunca al cliente.
  4. 4Tu servidorconsulta el perfil con el token, verifica el email y crea la sesión local.

1.0CREDENCIALES

Crea las credenciales en Google Cloud

Necesitas un ID de cliente OAuth 2.0 de tipo Aplicación web. Se genera en la consola de Google Cloud en unos cinco minutos; el paso que decide si el login funciona o falla es dar de alta el callback con exactitud. Ve paso a paso:

  1. Crea el proyecto. Entra en console.cloud.google.com con tu cuenta de Google. En la barra superior, junto al logo, abre el selector de proyectos y pulsa «Proyecto nuevo». Ponle nombre (por ejemplo login-flask) y confirma. Las credenciales viven a nivel de proyecto: si ya tienes uno para este fin, reutilízalo.
  2. Configura la pantalla de consentimiento. Menú lateral → «APIs y servicios» → «Pantalla de consentimiento de OAuth». Elige el tipo de usuario: Externo (cualquier cuenta de Google) o Interno (solo tu organización, si dispones de Google Workspace). Rellena el nombre de la app que verán las personas al iniciar sesión, el email de asistencia y añade tu correo en «Cuentas de prueba». Los scopes que pide esta app — openid email profile — no son sensibles, así que no necesitas pasar la verificación de Google para desarrollar.
  3. Genera el ID de cliente. Ve a «APIs y servicios» → «Credenciales» → «+ Crear credenciales» → «ID de cliente de OAuth 2.0». En Tipo de aplicación elige Aplicación web (el flujo lo completa tu servidor Flask). El nombre del cliente es solo informativo — por ejemplo flask-local.
  4. Dale de alta tus URLs. En el formulario de creación hay dos listas:
    • Orígenes JavaScript autorizados: http://127.0.0.1:5000. Solo lo exige si tu frontend llama a Google directamente desde el navegador; en este flujo todo pasa por el servidor, así que es opcional (no estorba).
    • URI de redirección autorizados: http://127.0.0.1:5000/login/callback. Imprescindible. Debe coincidir letra a letra —protocolo, host, puerto y ruta— con el redirect_uri que construya la app en la fase 3.0. Cualquier diferencia dispara el error redirect_uri_mismatch.
    Cuando despliegues en producción, añade en esta misma lista la URL pública del callback (por ejemplo https://tu-dominio.com/login/callback) — las URIs se pueden añadir más tarde editando el cliente.
  5. Guarda el secreto. Al pulsar «Crear», la consola muestra el client_id y el client_secret (también puedes descargarlos como JSON). Pégalos en tu .env — ese fichero ya está excluido en el .gitignore del proyecto. Si un secreto termina en un repositorio público, Google lo detecta de forma automática y lo revoca.
  6. Pruebas vs publicado. Mientras la pantalla de consentimiento esté «En pruebas», solo pueden iniciar sesión las cuentas que añadiste como usuarios de prueba. Con «Publicar aplicación» el acceso se abre a cualquiera — con scopes no sensibles, sin proceso de verificación. 
# .env — en la raíz del proyecto Flask, nunca en el repositorio
GOOGLE_CLIENT_ID=1234567890-abc123def456.apps.googleusercontent.com
GOOGLE_CLIENT_SECRET=GOCSPX-ejemplo_secreto
DATABASE=sqlite_db
OAUTHLIB_INSECURE_TRANSPORT=1

OAUTHLIB_INSECURE_TRANSPORT=1 solo permite http:// en desarrollo local — en producción fuera de ese fichero y todo por HTTPS.

2.0CONFIGURACIÓN

Centraliza la configuración en config.py

Una clase única lee las variables de entorno al arrancar y falla pronto si falta algo. La URL de descubrimiento de Google (OpenID Configuration) se mantiene aquí: con ella la app no hardcodea endpoints que Google puede mover.

3.0REDIRECCIÓN

/login: construye la URL de autorización

La ruta consulta el endpoint de descubrimiento, toma el authorization_endpoint actual y delega en WebApplicationClient la construcción de la URI con los scopes openid email profile y tu callback como destino.

4.0CALLBACK

/login/callback: canjea el código

Google devuelve el code por query string. La ruta lo prepara con prepare_token_request, lo canjea contra el token_endpoint autenticando con client_id + client_secret, y parsea la respuesta en el cliente para reutilizar el token en la llamada siguiente.

Sin code en la petición la ruta responde 400 — no intentes canjear nada.

5.0PERFIL

Obtén y verifica el perfil

Con el token en el cliente, la app llama al userinfo_endpoint y recibe sub (el identificador estable de Google), email, nombre y foto. El chequeo de email_verified es obligatorio: sin él, una cuenta no verificada podría suplantar a otra. 

if not userinfo.get("email_verified"):
    return "Email not verified by Google.", 400
6.0PERSISTENCIA

Crea (o recupera) al usuario en SQLite

user.py modela a la persona: User.get(google_id) la busca y User.create() la registra en el primer acceso. La clave primaria es el sub de Google — estable entre sesiones y no reutilizable por otros proveedores. El esquema exige email único.

7.0SESIÓN

Abre la sesión con Flask-Login

login_user(user) materializa la sesión y el decorador @login_required protege lo que toque. El cierre (/logout) limpia la sesión local; el usuario seguirá existiendo en la base de datos para el siguiente acceso.

CUANDO ALGO FALLA

Tres fallos que verás seguro.

redirect_uri_mismatch

El callback de la petición no coincide letra a letra con el dado de alta en Google Cloud. Incluye el puerto y la barra final tal cual.

invalid_grant

El code ya se usó o expiró (viven unos minutos y son de un solo uso). Recarga la página del callback no funciona: rehaz el login.

OAUTHLIB_INSECURE_TRANSPORT

Solo para desarrollo local con http://. Nunca lo actives en producción: ahí todo viaja por HTTPS y la variable ni se menciona.
